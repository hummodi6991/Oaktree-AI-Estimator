The first probe (`competitor_cross_source_overlap.sql`) sized cross-source
double-counting at overlap-share p50 0.379 / p75 0.433 / p90 0.500, but it
matched competitors with a **single token `'burger'`**, which is not how
production counts. Production (`_bulk_enrich_competitors`, the `UNION ALL`
at the `combined` CTE, `app/services/expansion_advisor.py:7503+`) matches:

- **restaurant_poi (Source 1):** `lower(rp.category) = ANY(:category_keys)`
  with `business_status IS NULL OR ='OPERATIONAL'`, where `category_keys` is
  `_expand_category(category)["keys"]`.
- **delivery_source_record (Source 2):**
  `lower(COALESCE(dsr.category_raw,'')) ~* :category_regex
   OR lower(COALESCE(dsr.cuisine_raw,'')) ~* :category_regex`,
  where `category_regex` is `_expand_category(category)["regex"]`.

The v2 probe mirrors that match exactly so the `_WHITESPACE_LOG_REF`
re-anchor is sized against an unbiased sample instead of a `'burger'`-only
slice.

### Code-verified findings BEFORE running the probe

1. **`cafe` POI keys match ~0 real `restaurant_poi.category` rows — artifact,
   not "no competitors".** `restaurant_poi.category` is assigned **only** via
   `normalize_category()` (`app/services/restaurant_categories.py:106`,
   driven by `app/ingest/restaurant_pois.py`). `normalize_category()` returns
   granular keys — `coffee`, `bakery`, `dessert`, `juice`, `burger`, `pizza`,
   `chicken`, `traditional`, `international`, … — and **never** the meta-bucket
   `coffee_bakery`. So the `cafe` key `{coffee_bakery}` matches no POI rows:
   in production, the same-category **POI** count for every `cafe`/`coffee`
   search is structurally **0**, and the entire cafe competitor signal comes
   from the **DSR side only**. Overlap for `cafe` is therefore ~undefined
   (no POI to dedupe against) and any cafe `poi_count`/overlap number is a
   measurement artifact. Result set **[C]** in the probe confirms this
   empirically (`poi_rows_matching_keys` for `cafe` ≈ 0). **Flagged, not
   silently reported as 0.** This is a real production observation worth a
   separate follow-up (the cafe POI leg is effectively dark), but it is out
   of scope for this sizing-only re-probe.

2. **`fast_food` key is also never produced by `normalize_category()`** — but
   `burger`/`pizza`/`chicken` (the other three `fast food` keys) are, so the
   `fast food` POI side is well covered; only the redundant `fast_food` key
   contributes nothing.

3. **`expansion_candidate.source_type` no longer exists.** It was dropped by
   migration `20260330_exp_adv_commercial_units`. The prompt listed it among
   the candidate columns; the probe does **not** reference it. (Used columns:
   `parcel_id, lat, lon, search_id, computed_at`, joined to
   `expansion_search.{id, category, service_model, created_at}`.)

4. **Radius note.** The probe uses the 1000 m qsr/dine_in/delivery_first
   competition radius per `_catchment_radii`. The `cafe` **service model**
   (distinct from the `cafe` *category*) actually uses an **800 m**
   competition radius in production (`_catchment_radii`,
   `app/services/expansion_advisor.py:837`). The 1000 m probe radius
   intentionally matches the three tight-radius models that carry a non-default
   `_WHITESPACE_LOG_REF` (qsr=75, dine_in=50, delivery_first=50); `cafe`
   service-model is on the default REF=25.

5. **DSR `geom`.** Confirmed present (migration
   `20260322_geom_indexes_dsr_pop`, trigger-synced from lat/lon). The probe
   resolves the `_dsr_has_geom` branch the same way production does and uses
   `geom` when present, else the lat/lon construct.

### Methodology (what the probe computes)

For each category, over ≤60 most-recent distinct candidate centroids pulled
from `expansion_candidate` joined to category-matched `expansion_search`
(1000 m radius):

- `poi_count` / `dsr_count` — production same-category match per source.
- `union_count` = poi + dsr (today's inflated count, no dedupe).
- A DSR row is an estimated **cross-source duplicate** when, within the same
  candidate radius, it matches ANY in-category POI by **(a)** normalized-name
  equality (`_CHAIN_NAME_NORM_SQL`) **or (b)** spatial proximity ≤75 m.
- `deduped_count` = union − duplicates; `overlap_share` = duplicates / union.
- Reports per-category and pooled **p50/p75/p90** of `union`, `deduped`, and
  `overlap_share`, plus a per-`service_model` anchor table (current vs
  suggested REF = deduped p90, rounded).
