## F1 — `_build_demand_thesis` ignores `demand_score_source` — **CONFIRMED**

**What the audit claimed:** the heuristic demand thesis always narrates
"population reach around {N}" even when `demand_score` was actually fed by the
demand-generator (dg) index composite, not population.

### Evidence

- `app/services/expansion_advisor.py:4176-4227` — `_build_demand_thesis`.
  The English string is hardcoded at **4210-4213**:
  `"Demand is {demand_label} ... with population reach around {population_reach:.0f}; ..."`.
  The structured record (id `"demand_thesis"`, **4216-4226**) carries only
  `demand_score`, `population_reach`, and the four labels — no dg signal.
- **Call site** `app/services/expansion_advisor.py:10646-10653` passes
  `demand_score`, `population_reach`, the provider/whitespace/competition
  scores and `delivery_observed` — **no dg-index inputs**.
- **dg inputs ARE in scope at the call site:**
  - `feature_snapshot_json["demand_score_source"]` is set at
    **10263** (value `"pop_score"` or `"dg_index"`, computed at 10096-10143),
    i.e. before the 10646 call.
  - `_dg_index_result` (computed once at **10074**) holds
    `composite_0_100` and `subscores` (`population`, `osm_generators`,
    `building_floors`, `fnb_review_weighted` — shape at
    `app/services/expansion_advisor.py:2218-2223`) and is emitted into
    `feature_snapshot_json["demand_generator_index"]` at **10254**.
  - So when `demand_score_source == "dg_index"`, the narrative still says
    "population reach around {N}" while the score was driven by the dg
    composite — a narrative-correctness mismatch.

### Emission / consumption paths (every backend leak + frontend renderer)

- **Persisted** on insert: `demand_thesis` and `demand_thesis_structured_json`
  columns (`expansion_advisor.py:11120`, `:11126`, INSERT params `:11193`,
  `:11199`, `:11247`).
- **Candidates list / report read-back:** selected at `:11486/:11493`,
  `:11814`, `:12110/:12117`; surfaced via `_normalize_candidate_payload`
  (`:11903`, `:12237`).
- **AR re-render contract:** `_normalize_candidate_payload` (`:1367-1369`)
  re-renders `demand_thesis` from `demand_thesis_structured_json` via
  `expansion_advisor_i18n.render(...)` **only on `lang=="ar"`**; the `en`
  branch (`:1392`) passes the persisted English string through byte-for-byte.
- **i18n template:** `app/services/expansion_advisor_i18n.py:186-196` — the
  `"demand_thesis"` template's `en` side is **byte-identical** to the
  producer's f-string (PR #2b contract). A dg-aware variant must NOT mutate
  this template or the `"demand_thesis"` id, or it breaks the byte-identity
  golden.
- **Frontend renderers (reach AR users):**
  - `frontend/src/features/expansion-advisor/CandidateDetailPanel.tsx:43`
    renders `candidate.demand_thesis` directly.
  - `frontend/src/features/expansion-advisor/AdvisorySectionCards.tsx:144`
    renders `section.demand_thesis`.
  - API type: `frontend/src/lib/api/expansionAdvisor.ts:248,359,461,513`.
- **Distinct from the LLM memo:** `app/services/llm_decision_memo.py` has its
  own `demand_thesis` (LLM-filled, `:566`, `:1528`) inside the structured
  decision memo — **out of scope** for this finding; F1 is only the heuristic
  thesis.

### Test coverage (pins the current behavior)

- `tests/test_pr2_english_byte_identity.py` + 9 goldens
  `tests/fixtures/pr2_golden/dt_01..dt_09.json` pin the exact English
  `demand_thesis` string and structured record.
- `tests/test_pr2b_arabic_render.py` pins the AR render.
- **Implication:** the existing `"demand_thesis"` id must keep rendering
  byte-identically. A new id is the safe shape.

### Recommended action — Patch (P2)

Introduce a **new structured id** `"demand_thesis_dg"` (new i18n template
en+ar), emitted only when `demand_score_source == "dg_index"`, carrying the dg
composite and the leading subscore(s) so the narrative can say e.g. "demand is
driven by a high generator index (offices/retail/foot-traffic)" instead of
"population reach around N". Keep the existing `"demand_thesis"` id and template
untouched for backward compatibility with persisted rows and the byte-identity
goldens. **Do NOT** add params to the existing record (would break the golden
fixtures and pre-existing persisted rows that render via the same template).
Persisted pre-patch rows keep `id="demand_thesis"` and render exactly as today
(rule #4 fallback intact).

## F2 — Cross-source competitor double-count — **CONFIRMED (magnitude needs DB probe)**

### Evidence

- `app/services/expansion_advisor.py:7498-7538` — inside
  `_bulk_enrich_competitors`, Source 1 (`restaurant_poi`, Google) and Source 2
  (`delivery_source_record`, HungerStation etc.) are combined with **`UNION
  ALL`** (`:7522`) and counted by `COUNT(*) FILTER (WHERE in_category)`
  (`:7461`). **No cross-source dedupe** (no name, no spatial). A venue listed on
  both Google and a delivery platform is counted twice in `competitor_count`.
- This `competitor_count` / `broader_count` feeds `provider_whitespace_score`,
  `delivery_competition_score` and the chain-strength share — i.e. it propagates
  into ranking, not just display.

### Anchor-recalibration warning (per the prompt)

- `_WHITESPACE_LOG_REF` (`app/services/expansion_advisor.py:2789-2820`):
  `dine_in=50.0`, `delivery_first=50.0`, `qsr=75.0`, default `25.0`. The inline
  comment explicitly states these were sized against **probe counts that
  under-count** (simplified category match, no alias expansion) and were set
  HIGH to avoid re-flooring on the alias-expanded production counts. They were
  therefore calibrated on the **inflated (un-deduped) UNION ALL counts**. Any
  cross-source dedupe shrinks the counts and **requires re-anchoring** the REF
  values downward — otherwise the log curve floors a larger share of the
  shortlist at 15.0.

### Magnitude — run the probe

`scripts/diagnostics/competitor_cross_source_overlap.sql` quantifies, per recent
qsr/burger candidate centroid (1000 m competition radius):
- same-category POI count, same-category DSR count, UNION ALL count,
- estimated overlap via normalized-name match (inline `_CHAIN_NAME_NORM_SQL`
  mirror) **and** 75 m spatial proximity,
- overlap-share p50/p75/p90, and the **deduped count** p50/p75/p90 so the
  anchor shift can be sized: re-anchor REF roughly to the deduped p90 tail the
  same way the current comment sizes REF to the un-deduped tail.

**Caveat baked into the probe:** simplified single-token `'burger'` match
(under-counts vs `_expand_category`); the overlap SHARE is the robust output,
absolute counts are a lower bound.

### Test coverage

- **None.** No test references `_bulk_enrich_competitors` or cross-source
  dedupe. Behavior is unpinned — a dedupe patch will not fight a fixture, but it
  also has no regression net; add one with the patch.

### Recommended action — Probe-first (P1)

Quantify with the probe; do **not** patch yet. The eventual dedupe and the
`_WHITESPACE_LOG_REF` re-anchor must land together (and with a new test),
because dedupe without re-anchoring degrades whitespace discrimination.

## F3 — Locale ping-pong memo regeneration — **CONFIRMED**

### Evidence

- `app/services/expansion_advisor.py:12009-12071` —
  `_regenerate_candidate_memo_in_locale` issues a single UPDATE (`:12046-12062`)
  setting `decision_memo`, `decision_memo_json`, `decision_memo_prompt_version`,
  `decision_memo_lang` — **one storage slot**, no per-locale columns.
- Fired by `get_candidate_memo` at `:12320-12332`: when
  `lang != (stored_lang or "en")` and a memo exists, it regenerates **and
  persists** in the requested locale. So AR→EN→AR re-generates every time and
  flips the single slot back and forth; each flip is one synchronous
  `EXPANSION_MEMO_MODEL` call from a GET handler (cost note acknowledged in-code
  at `:12317-12319`).

### Migration history (per-locale storage never existed)

- `alembic/versions/20260414_memo_json.py` — adds `decision_memo` (TEXT),
  `decision_memo_json` (JSONB).
- `alembic/versions/20260425_memo_prompt_version.py` — adds
  `decision_memo_prompt_version` (TEXT).
- `alembic/versions/20260519_decision_memo_lang.py:34` — adds
  `decision_memo_lang` (String(8)), nullable, **no backfill**.
- No migration ever added per-locale storage; single-slot by construction.

### Production amplifier

`k8s/deployment.yaml:38-39` sets `EXPANSION_MEMO_PREWARM_ENABLED=false` in
production — so the **on-demand regenerate-on-mismatch is the ONLY memo
generation path in prod**. Every memo is generated on first GET and re-generated
on every locale flip. F3 is fully live in production.

### Quantify

`scripts/diagnostics/memo_locale_flips.sql` reports current resting-locale
counts, prompt-version distribution, AR-resting row count, and total
memo-bearing rows. **There is no request/audit log table** (`decision_memo_lang`
is the only locale record), so historical flip frequency cannot be derived from
the DB — pull GET `/candidates/{id}/memo` access patterns from API logs for
true flip rate.

### Cost per flip

`EXPANSION_MEMO_MODEL` (config default `gpt-4o-mini`,
`app/core/config.py:191`; production value from the `oaktree-app-env` secret —
read via kubectl) at `EXPANSION_MEMO_MAX_TOKENS` (default 2400,
`app/core/config.py:192-193`) completion tokens plus the memo-context prompt,
**per flip**.

### Test coverage (pins single-slot behavior)

- `tests/test_pr4a_arabic_structured_memo.py::TestRegenerateOnMismatch`
  (`:391-426`) pins: EN-stored + AR-request triggers exactly one regeneration
  and **one** UPDATE with `lang="ar"`, committed. A per-locale-storage patch
  must update this test (the single-UPDATE assertion changes).

### Recommended action — Patch (P1)

Recommended storage shape: a **JSONB `{en, ar}` map** column
(`decision_memo_by_lang` / `decision_memo_json_by_lang`) so each locale is
cached independently and a flip becomes a cheap read, not a model call. Two
flat columns per locale (`decision_memo_en`/`decision_memo_ar` + json peers)
also work and are simpler to query but rigid if more locales appear. Migration
sketch (no code in this PR): additive columns, backfill the existing single slot
into the `decision_memo_lang`-keyed entry, keep the legacy columns readable for
one release (rule #4 fallback). Run the probe first to size the AR-resting
population that benefits.

## F6 — `_percentile_rent_burden` N+1 in the first scoring pass — **CONFIRMED (magnitude needs DB probe)**

### Evidence

- First-pass loop: `app/services/expansion_advisor.py:8750` (`for row in
  rows:`) calls `_economics_score(db=db, is_listing=_is_listing, ...)` at
  **9033-9047** for the FULL pool. Shortlisting happens **after** the loop
  (`shortlist_size = min(len(prepared), max(limit, 25))` at **9193**) — so
  economics (and its rent-burden queries) run for the entire pool, not the
  shortlist.
- `_economics_score` (`:5363`) calls `_percentile_rent_burden` when
  `is_listing and db is not None` (**5401-5410**).
- `_percentile_rent_burden` (`:5114-5339`) builds a fallback `chains` list of up
  to **5 rungs** (`district_band_type`, `district_type`, `district` — `:5225-5242`;
  `city_band_type` — `:5244`; `city` — `:5250`) and runs **one aggregate query
  per rung** (`:5257-5287`), breaking early when a rung meets its `min_n`. Worst
  case (thin district data) = 5 aggregate scans **per listing**, with **no
  per-search caching** — each call re-runs the chain from scratch.
- Each aggregate scans the envelope-filtered `commercial_unit` set
  (`base_where` `:5187-5198`).

Note: `_economics_score` is also called a **second time** per shortlisted
listing in the second pass (`:10205-10220`, this time WITH
`cand_age_days`); the N+1 over the *full pool* is the first-pass cost.

### Magnitude — run the probe

`scripts/diagnostics/pool_size_recent_searches.sql`:
- §1 persisted candidate + listing counts for the last 20 searches (a floor on
  pool size; the true pool `len(rows)` is **not persisted**).
- §2 global upper bound = active restaurant-suitable Tier-1 listings.
- §3 comparable population each aggregate scans.
- §4 distinct `(neighborhood, listing_type)` cells — i.e. how much a per-cell
  cache would collapse.

**True pool size and latency come from pod logs** (not the DB):
- pool: `"expansion_search timing: candidate_query=...s search_id=... rows=N"`
  (`app/services/expansion_advisor.py:8330-8332`).
- pool cap context: `"expansion_advisor.candidate_pool_cap ...
  candidate_pool_limit=..."` (`:8158-8163`).
- p50/p95 latency: `"expansion_report timing: total=...s ..."` (`:12549`) and
  `"expansion_memo timing: ..."` (`:12192`).

**Query-count upper bound per search** ≈ `listing_rows_in_pool × 5` aggregate
queries (worst case), independent of how many resolve early.

### Memoization design (sketch, no code)

Per-search cache keyed by comparable **cell** `(label, neighborhood, band_lo,
band_hi, ltype)`. For each cell, fetch the comparable **rate array** (and each
comparable's age-basis date `COALESCE(aqar_created_at, first_seen_at)`) **once**;
compute median + `n` at cell level (cacheable). Then per candidate compute:
- `n_below` = count of cached rates `<= listing_monthly_rent_per_m2` (per-candidate
  threshold → computed in Python from the cached array), and
- `n_older` = count of cached age-basis dates whose age `>= cand_age_days`
  (per-candidate threshold → also Python-side from the cached array).

This keeps the **`cand_age_days` per-candidate term correct** under caching:
only the cell's raw array is shared; `n_below` and `n_older` are recomputed per
candidate against the cached array, so the percentile and `age_percentile` stay
candidate-specific. The 5-rung fallback still applies, but each distinct cell is
fetched at most once per search.

### Test coverage

- `_percentile_rent_burden` correctness is exercised indirectly via
  `tests/test_expansion_advisor_service.py` / `_regression`, but **no test pins
  per-search caching or query count** (caching does not exist yet). A memoized
  implementation must keep the existing numeric outputs identical.

### Recommended action — Probe-first (P1)

Run the probe to confirm pool/listing sizes and cell-sharing, then memoize. Keep
outputs byte-identical to today (correctness over speed).

## F7 — `_delivery_observed` comment drift — **CONFIRMED**

### Evidence

- `app/services/expansion_advisor.py:8877-8882`:
  - Comment (`:8877-8878`): *"Thresholds: ≥3 total listings OR ≥2 platforms OR
    ≥1 same-category competitor in the delivery radius."*
  - Code (`:8879-8882`):
    `provider_listing_count >= 5 OR provider_platform_count >= 2 OR
    delivery_competition_count >= 2`.
  - **Two drifts:** listings `≥3` (comment) vs `>= 5` (code); same-category
    `≥1` (comment) vs `>= 2` (code). Only platforms (`≥2`) agree.

### Which is intended?

- `git blame` attributes both comment and code to the same boundary commit
  `^7d62fd182` (the clone is shallow; history is truncated there). `git log -S
  "provider_listing_count >= 3"` returns **nothing** — the code was never
  literally `>= 3` in the available history; `>= 5` has been stable throughout.
- The code's `5 / 2 / 2` thresholds are internally consistent and stable; the
  comment is the stale artifact. Changing the thresholds back to `3 / 1` would
  alter `_delivery_observed` for every thin-data candidate (it gates
  `provider_density_score` / `provider_whitespace_score` at `:8884+`), i.e. a
  **scoring semantics change** — not something to do on the strength of a stale
  comment.

### Test coverage

- No test pins the `5 / 2 / 2` threshold values directly
  (`tests/test_expansion_advisor_service.py` exercises the surrounding scoring
  with various counts but does not assert the boundary).

### Recommended action — Docfix (P3), flag ambiguity

Update the comment at **8877-8878** to match the code (`≥5 listings OR ≥2
platforms OR ≥2 same-category`). Do **not** change the thresholds. If `3 / 1`
was ever the *intended calibration* (cannot be confirmed from the truncated
history), that is a separate scoring change requiring re-validation — raise it
with whoever owns the delivery-observation calibration before touching the
numbers.
